How it works

One policy. Two call sites. Zero trust in prose.

The model never decides who gets paid. It produces typed fields and an explanation. The same rules.ts runs in the agent to explain, and inside the reducer transaction to decide.

01

Read

Claude reads the rendered invoice, rate confirmation, POD, NOA and emails. It returns typed fields with a confidence score and a plain-language explanation. It cannot touch assignments, bank records or approvals.

02

Decide

Ten deterministic rules in rules.ts select the amount from the rate con and the payee from verified assignments. Any failed rule is a hold with the rule id, reason and evidence ids attached.

03

Enforce

SpacetimeDB reducers re-run the policy on trusted rows, reserve the load and invoice key atomically, and derive the actor from the connection identity. The agent identity cannot approve. Refusals commit to the audit log.

Three stories

Proven on freight, where payment-redirect fraud is worst.

Three seeded loads run end to end through the same path: documents in, decision out, approval by a different human, payment status that never lies.

Payment lifecycle

Submitted is not settled.

pending ──▶ approved ──▶ submitting ──▶ submitted ──▶ simulated_settled
   │            │              │              │
rejected     pending*       unknown         failed
                               │
                      submitted / failed

pending*  prior approval invalidated when the snapshot changes
unknown   obligation stays reserved; reconcile the stored key
Unknown is not failed.
Unknown is not permission to pay again.A timeout after a possible send never creates a new payment identity. The runner restarts, finds its stored idempotency key, and reconciles to one transfer.
